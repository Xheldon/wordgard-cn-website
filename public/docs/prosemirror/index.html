从 ProseMirror 迁移

Wordgard 是 ProseMirror 设计的又一次迭代。它采用了许多相同的理念，但实现方式往往有所不同。本文档总结了这些变更，以帮助熟悉 ProseMirror 的用户快速上手。

本系统在设计之初并未旨在提供兼容接口。其命名规范和库结构均是从头构建的，因此任何与 ProseMirror 交互的代码都必须重写才能与 Wordgard 配合使用。不过，许多底层概念是相同的，因此通常相同的解决方案仍然适用，您只需将现有代码适配到 Wordgard 的接口即可。

Wordgard 的核心以单个软件包（wordgard）的形式分发，但由多个独立的模块组成，这些模块的导入方式例如为 "wordgard/state"。模块之间的映射大致如下：

  • wordgard/doc：prosemirror-model、prosemirror-transform
  • wordgard/state: prosemirror-state
  • wordgard/history：prosemirror-history
  • wordgard/command：prosemirror-commands
  • wordgard/types：prosemirror-schema-basic、prosemirror-schema-list
  • wordgard/schema：用于模式元素的现成扩展
  • wordgard/collab: prosemirror-collab
  • wordgard/editor：prosemirror-view、prosemirror-menu、prosemirror-keymap、prosemirror-inputrules

文档模型

Wordgard 的文档模型在基本结构上与 ProseMirror 相似。您仍然需要定义节点和标记，以及它们的嵌套方式，文档仍然是一个节点树，每个节点都带有一组标记。

Wordgard 引入了术语 plot（用于非叶节点），并更严格地将其与 leaves（无法包含内容的节点）区分开来。它还引入了 tag 的概念，该概念既可以是完整的叶节点，也可以是 plot 的 {type, parameter, marks} 部分。plot 对象本身包含一个 tag 和一个内容数组。节点的 content 直接暴露为数组，不再需要通过访问器方法访问。

文档结构的工作方式发生了三个根本性变化：

  • 内容表达式已不再存在。您只能提供一组有效的内容节点类型，此外，对于块内容图，还需指定该图是否可以为空。任何关于父子关系的进一步限制都需要在文档级别之上进行处理，例如在Correction中。
  • 节点上是否允许出现标记不再由父节点控制，而是由标记本身控制。
  • 节点现在不再拥有多个属性，而是只有一个参数值。可选属性通过标记来建模。

职位

文档索引系统的工作方式与 ProseMirror 相同。节点现在具有 length 属性而非 size 属性，用于指示其总标记数。

解析后的文档位置由 Pos 类表示，同时还有一个独立但类似的类用于表示 节点位置。它们的接口与 ProseMirror 的 ResolvedPos 对象相似，只是稍微不那么令人困惑。

Selection 对象存储原始位置，而不是像 ProseMirror 中那样存储解析后的位置，但状态允许通过其 sel 属性 轻松访问解析后的选择边界。

架构结构

Wordgard 架构比 ProseMirror 的架构更不具单体性。节点或标记类型存在于架构之外，并可在不同架构之间共享。由于额外属性是通过标记来建模的，因此您可以为节点类型定义这些属性，而无需修改节点类型本身。

特定模式可以修改节点与标记之间的关系，而无需重新定义节点或标记本身。其效果是，这些模式元素在不同模式间更容易复用，并且与 ProseMirror 相比，利用现有的节点或标记实现来组合模式也更加便捷。

父子关系上较为简单的约束也意味着，编写适用于任何模式的文档操作代码变得更加容易，而这在 ProseMirror 中是一项非常棘手的任务。

节点声明旨在更具声明性，通过将序列化和解析信息合并到单个字段中，以处理简单节点。此类声明返回一个节点类型（或者，如果该类型没有参数，则返回一个标签），该类型或标签可作为模式的一部分使用。

const CodeBlock = Plot.define("CodeBlock", {
  inlineContent: true,
  group: Node.Group.Content,
  role: Node.Role.Code,
  shape: {element: "pre"}
})

每种类型仍然拥有一个用于 JSON 序列化和调试输出的字符串名称，但它在 API 中的作用不如在 ProseMirror 中那么重要。您通常通过对象而非字符串名称来引用节点类型。

配置

Wordgard 继承了 CodeMirror 的扩展系统，该系统基于 facets，几乎完全未作改动。这意味着扩展点不再局限于有限的编辑器或插件属性，而是成为了一等公民；无论是库内部还是您自己的代码中，只需几行代码即可定义新的扩展点。

由于面向切面的配置方式使得扩展点能够以可组合的方式进行定义，并且优先级系统允许在需要时控制扩展的优先级，因此在该系统中，通过引入不同的打包扩展来配置编辑器要容易得多。

编辑器配置是一个扩展树，与 ProseMirror 的扁平插件数组不同，它允许给定的扩展包包含任意数量的子扩展，这些子扩展是比 ProseMirror 插件更细粒度的单元。插件状态现在通过状态字段建模，视图插件作为独立实体存在，而属性已被面（facets）取代，声明时不再需要附加到插件上。

架构的构建是在配置时通过将配置中发现的架构元素组合而成的。这意味着，通常只需插入一个列表扩展，即可在您的架构中启用列表支持。

其他支持性扩展，例如菜单项定义或键盘绑定，也可以包含在同一个扩展包中。总体而言，配置 Wordgard 应该比配置 ProseMirror 简单得多，尤其是在您不需要更改大量默认设置的情况下。

核心 Wordgard 库包含一个即插即用的菜单实现。

交易与变更

Wordgard 的文档变更模型与 ProseMirror 的步进模型完全不同。事务的创建机制也截然不同，其设计灵感更多来自 CodeMirror，而非 ProseMirror。

变更

Wordgard 文档变更代表对文档的一次完整遍历，替换部分范围并保留其他范围，同时可选择为保留的范围添加或删除标记。它以“差异”格式存储，表现为覆盖旧文档的一系列段落。

此类变更集可以相互组合或转换。与 ProseMirror 步骤序列相比，它们更易于操作和检查。

位置映射的工作原理类似，不同之处在于映射和变更不再是分开的，而是由同一个 对象 表示。变更集拥有一个 mapPos 方法，可将变更前的位置转换为变更后的位置。

在组合变更（例如构建事务）时，所有单独的变更均基于原始文档的索引系统进行指定。因此，与 ProseMirror 不同，无需针对其他变更所产生的偏移量进行调整。从概念上讲，这些变更是同时发生的。

切片

在 ProseMirror 中，切片（Slices）是节点的序列，这些节点可能是部分节点，并且切片在起始和结束处具有开放深度。在 Wordgard 中，变更被建模为被替换的令牌（这些令牌可以是情节的开头、情节的结尾、叶节点或文本字符），因此切片是令牌的序列。此处使用节点（叶节点或非叶节点）代表其自身，使用情节标签代表开始令牌，并使用一个特殊值代表情节结束令牌。

在变更规范中，通过 insert 属性传入的数组是一个令牌数组。

交易

ProseMirror 事务是可变对象，它们使用方法链来累积构成事务的各个部分。Wordgard 则使用从 规范对象 创建的不可变对象。

wg.dispatch({
  changes: [
    {from: 1, insert: [someNode]},
    {from: 8, to: 10, add: Strong},
    {from: 20, to: 30}
  ],
  selection: {anchor: 2},
  scrollIntoView: true
})

事务仍然是描述编辑器状态整体变更的对象。新状态通过读取其 state 属性 来获取，而不是显式地应用它们。该状态类称为 GardState，与 ProseMirror 的 EditorState 非常相似。

ProseMirror 所称的事务元数据在 Wordgard 中被称为注解。此外，还有一个效果的概念，它在某种程度上类似于注解，但不同之处在于，它不是描述整个事务，而是表示该事务对状态产生的特定影响，并且可以随变更进行映射。

编辑器对象仍然具有一个dispatch方法，这是更新编辑器状态的方式。您通常只需向其传递一个规范对象，而不是构造的事务对象。

编辑

在 ProseMirror 中，编辑器组件 EditorView 被称为 Wordgard。它仍然将文档渲染为可编辑的 DOM，处理编辑事件，并支持文档装饰。

输入

得益于浏览器的改进，或者至少是因为一些表现极差的浏览器最终变得不再重要，Wordgard 更多地使用了 `beforeinput` 和 `input` 事件，因此在读取输入时，无需像 ProseMirror 那样采取一些奇特的处理方式。不再需要解析变更后的 DOM 结构。

针对组合操作的临时解决方案（即编辑器必须小心避免触碰浏览器正在进行组合操作的文本节点）仍然需要，但实现方式已变得相对不那么复杂。

由于 ProseMirror 将鼠标和键盘的选择操作完全交由浏览器的原生实现处理，这成为了无尽问题的根源，因此 Wordgard 接管了这一功能，并在库内部自行处理。这意味着所有与选择相关的按键都绑定了自定义命令，且该库会自行处理双向文本。

光标

另一个常见问题是浏览器的原生光标未出现在正确位置（或根本未显示）。为了控制这一点，Wordgard 会隐藏原生光标并绘制自己的光标。

原生（非光标）选区保持可见，因为它似乎引起的麻烦更少。

更新

ProseMirror 中最大的错误之一是，编辑器视图在更新时无法访问事务对象，只能访问状态。Wordgard 没有重蹈这一覆辙，而是让更新操作接收事务对象，而不仅仅是新的状态。

这意味着诸如 DOM 更新逻辑和 UI 插件等组件可以精确地观察发生的变化，并以更高效、更有效的方式处理变更。ProseMirror 中仍存在的奇怪且意外的 DOM 重绘问题将不再出现。只有受新事务影响的精确 DOM 结构才会被更新。

Wordgard 会异步更新其 DOM 结构，而 ProseMirror 则是同步更新。当您尝试通过诸如 posAtCoords 之类的方法访问该结构时，Wordgard 会隐式地进行急切更新。

命令

编辑器 命令 使用的签名类型比 ProseMirror 中的更直观。它们是从编辑器和一个可选参数到布尔值或事务规范的函数。当在 菜单项 或 键盘绑定 中使用它们时，您可以将参数 绑定 到命令上。

与 ProseMirror 命令不同，Wordgard 命令允许扩展注册额外的 处理程序，以便在特定情况下影响其行为。

键盘绑定 在您的配置中作为独立的对象提供，而不是收集在映射中。（这些对象本身被视为扩展。）

装饰品

装饰的基本原理——即它们以集合形式提供并影响其所指向的节点——在 Wordgard 中与在 ProseMirror 中相同。Wordgard 将 点 装饰（影响单个点的装饰）与 范围 装饰（影响内容范围的装饰）区分开来，并针对两者使用不同的数据结构。

这些数据结构（PointSet 和 RangeSet）也可用于非装饰值，如果您需要以与文档位置关联的方式存储某些内容，并允许通过文档更改进行 映射。

此外，Wordgard 还支持 “标签”装饰，它们会影响整个文档中的特定节点类型，而不仅仅是某个特定位置。这些装饰会替换节点视图，并允许实现一些新功能，例如在节点旁边放置小部件，或将它们包裹在额外的 DOM 结构中。

要指定装饰的 DOM 结构（或更复杂节点类型的默认结构），Wordgard 使用了 Elt 抽象，它类似于 ProseMirror 的 DOMOutputSpec 或 JSX 语法，即创建一个描述 DOM 树片段的 JS 对象，而无需实际创建该 DOM 树。
