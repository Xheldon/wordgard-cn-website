常见问题解答

此处是我收集问题答案的地方，以便我可以链接到这里，而无需重复自己。运气好的话，有些人甚至会在提问之前就找到答案。

1.0 版本何时发布？

完成后。根据以往项目的经验，我发现让使用者先使用一段时间该库，以便发现哪些部分会引发问题，然后在必要时进行破坏性更改以解决这些问题，是非常有价值的。因此，请不要抱太大期望。这可能需要一到两年的时间。

为什么不接受拉取请求？

原因有几个：

  • 我是一个控制狂，很难接受不经过重写以符合我对系统之道的精确构想的代码。

  • 我并不太喜欢审查代码。我反感这种动态：人们可以将一堆烦人的工作推到我身上，并暗示如果我不处理就是粗鲁或疏忽；同时，当我对他们的工作不满意时，还得费心委婉地拒绝他们。

  • 不采用拉取请求（PR）是有效扼杀人们提交由大语言模型生成的低质量代码这一问题的萌芽的方法。

这是我的禅意花园。欢迎您报告错误、提出改进建议，或对我糟糕的设计品味大发雷霆。但如果您希望拥有我不愿构建和维护的功能，那就请您自行开发一个模块来实现。

“社会期望”的支持是否构成一种威胁？

不。我在首页这样表述，是为了向商业用户明确：期望获得维护良好的开源组件，却不支持其维护者，这种做法是不可持续的。但我不会特意去羞辱那些使用我的软件却未提供资金的公司，除非他们以其他方式惹恼了我。

你不知道 TypeScript 命名空间不利于树摇吗？

我确实知道，甚至不惜在库的构建系统中添加糟糕的变通方案，以修复这些针对 TypeScript 2005 年代风格输出的问题。

借助这一权宜之计，如果未被引用，各个命名空间至少可以被 Rollup 消除。再加上每个命名空间仅封装了一组连贯的功能，而这些功能通常作为一个整体被需要，因此，如果需要该库，它应该能很好地支持树摇优化。

话虽如此，由于 JavaScript 中的死代码消除非常混乱，而库作者可用的辅助工具又极其粗糙，因此我不确定其他工具在处理这一问题时的表现如何。
