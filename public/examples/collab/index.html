示例：协同编辑

实时协同编辑是一种允许多个用户在不同机器上同时编辑同一文档的技术。更改通过网络传播给其他参与者，并在到达后立即显示在他们的文档视图中。

这是一个位于本页面内的玩具协作编辑环境。它通过异步文本通道在编辑器之间共享更新，以模拟网络环境。

Server

这种编辑方式的主要难点在于处理冲突的编辑——由于通信并非即时，人们可能同时做出更改，因此在重新同步所有人时，必须以某种方式解决这些冲突。

Wordgard 提供基于操作转换（Operational Transformation）的协同编辑功能，该功能由一个中央权威（服务器）负责为变更分配确定的顺序。本示例将介绍如何搭建协同编辑服务器的完整流程。

代码被有意保持简单。它几乎不进行任何输入验证或错误检查，也不处理重连等情况。真正的实现，尤其是在服务器端，将会复杂得多。

（计划最终将此类服务器纳入 Wordgard 发行版，但尚未完成。）

还存在其他协同编辑方法（尤其是基于CRDTs的方法），它们具有不同的权衡。本示例描述的是随 Wordgard 捆绑的方法，但最佳方案将取决于您的具体用例。

算法

操作转换通过定义一种方法，使两个均期望从文档 D 开始的变更 A 和 B 能够相互转换，从而生成转换后的变更 A' 和 B'。这些转换后的变更可应用于由对方步骤生成的文档，使得在 A 之后应用 B' 与在 B 之后应用 A' 均能产生完全相同的文档。

Wordgard 变更集通过 transform 支持此功能。该原语可用于协调不同编辑器对同一文档并发执行的步骤，确保最终所有用户都获得相同的文档。

由于完全以分布式方式实现这一点十分困难，我们依赖一个中央进程（即服务器）来协调客户端之间的变更交换。客户端向服务器告知其所做的变更。服务器为这些变更确定一个统一的顺序，然后将其发送回所有客户端；各客户端以特定方式应用他人所做的变更，使得尽管它们最初可能以不同的顺序执行了自己的变更，但最终所有客户端都能获得相同的文档。

更具体地说：

  • 服务器拥有一个当前文档，并为该文档分配了一个版本号。此外，它还保留至少最近的历史变更记录。

  • 客户端会跟踪其上次同步的服务器文档版本，以及在此基础上所做的更改。当存在 本地更改 时，客户端会尝试将这些更改连同上次同步的文档版本和唯一的客户端 ID 一起发送到服务器。

  • 当服务器接收到从其当前文档版本开始的变化时，它可以原样接受这些变化，将其添加到变化列表中，更新其文档和版本，并将其发送出去。
  • 当接收到基于过时文档发起的变更时，服务器可以在本地对这些变更进行转换，并接受转换后的版本。这并非绝对必要，因为客户端最终会自行转换这些变更并重试，但这样做能显著提升吞吐量，并防止因慢速客户端不断被快速客户端超越而导致其变更无法发出的问题。
  • 当客户端 接收 到由他人发起的来自服务器的变更时，如果它没有待处理的本地变更，则可以直接应用该变更。如果存在待处理的本地变更，则它需要将远程变更与本地变更相互转换，以便应用转换后的远程变更，并将其待处理变更集更新为转换后的版本，从而确保这些变更仍然从服务器在此版本所持有的文档开始。接收操作还会将客户端的同步文档版本更新为应用所接收变更后的文档版本。
  • 为了在网络故障面前保持健壮性，客户端会等待其自身的变更从服务器返回，然后才将其视为已确认。因此，此类变更与其他变更一样到达，但可以通过其关联的客户端 ID 进行识别。当接收到此类变更时，客户端会从其待处理变更集中移除该变更，并再次更新其已与服务器同步的文档版本。

跟踪此客户端状态是通过 collab 插件 完成的。要使用接收到的更改更新编辑器，您需要分派由 collab.receive 生成的事务。为了组织将本地更改发送到服务器，您通常需要使用更新处理器或插件。

服务器

我们的客户端和服务器将通过简单的 JSON 协议进行通信。客户端仅发送包含其所做的更改（以及该更改所对应的文档版本）的更新消息。

type ClientMessage =
  {type: "update", changes: ChangeSet.JSON, version: number}

服务器将发送一条初始化消息，向新连接的客户端提供当前文档、版本及其唯一标识符。除此之外，服务器仅发送更新内容，或在出现错误时发送错误消息。

type ServerMessage =
  {type: "state",
   doc: Node.JSON, version: number, clientID: string} |
  {type: "update",
   changes: ChangeSet.JSON, clientID: string, version: number} |
  {type: "error", error: string}

这些消息通过一个粗糙的通信通道抽象发送，该抽象是一个具有 send 方法的对象，并且是一个异步迭代器，用于以字符串形式生成消息。

interface Channel {
  send(message: string): void
  messages: AsyncGenerator<string>
}

更新以 StoredUpdate 类型的对象形式存储。由于需要在转换过程中保持文档格式良好，Wordgard 的 转换操作 需要访问变更起始的文档。因此，每个更新还会保留其起始文档。此示例服务器将所有更新存储在内存中。在实际的服务器中，您通常只保留最近的更新（以便对稍过时的传入变更进行转换）。

type StoredUpdate = {
  doc: Plot.Doc
  changes: ChangeSet
  clientID: string
  version: number
}

为了确定向谁发送更新，服务器会维护一个活跃客户端集合。对于网络服务器而言，这些客户端可能是那些与服务器保持 WebSocket 连接的客户端。

type ActiveClient = {id: string, channel: Channel}

function send(client: ActiveClient, message: ServerMessage) {
  client.channel.send(JSON.stringify(message))
}

服务器是一个简单的对象，用于保存当前文档、更新历史记录以及已连接客户端的数组。

class Server {
  doc: Plot.Doc
  version: number = 0
  updates: StoredUpdate[] = []

  clients: ActiveClient[] = []
  nextClientId = 1

  constructor(doc: Plot.Doc) {
    this.doc = doc
  }

  connect(channel: Channel) {
    let client: ActiveClient = {
      id: "client_" + this.nextClientId++,
      channel
    }
    this.clients.push(client)
    send(client, {
      type: "state",
      doc: this.doc.toJSON(),
      version: this.version,
      clientID: client.id
    })
    this.listen(client).catch(e => console.error(e))
  }

  async listen(client: ActiveClient) {
    for await (let json of client.channel.messages) {
      let msg = JSON.parse(json) as ClientMessage
      if (msg.type != "update")
        throw new Error("Unexpected client message: " + json)
      let changes = ChangeSet.fromJSON(this.doc.schema, msg.changes)
      this.receive(client, changes, msg.version, client.id)
    }
  }

当新客户端连接时，它会被添加到活动客户端集合中，并收到一条初始化消息。随后，在其消息通道上启动一个异步监听循环，当该客户端发送更新时，该循环会调用 receive 方法。

如果客户端发送的更新与当前最新版本不匹配，服务器会首先尝试对其进行转换。同样，这一步并非绝对必要；例如，如果您不再拥有必要的变更数据，也可以跳过此步骤。一旦客户端收到其在发送该更新时尚未获取的更新，它将在本地对该变更进行转换，并再次尝试提交。

当 transorm 返回 null 时，表示服务器已知该变更，因此不会再次尝试应用它。

最后，该变更被添加到历史记录中，当前文档得到更新，并且变更被广播给所有客户端。

  receive(
    client: ActiveClient,
    changes: ChangeSet,
    version: number,
    clientID: string
  ) {
    if (this.version > version) {
      let mapped = collab.transformUpdate(
        {changes, version, clientID},
        this.updates.slice(version))
      if (!mapped) return
      ;({changes, version, clientID} = mapped)
    }
    let update: StoredUpdate = {
      doc: this.doc,
      clientID, changes,
      version: this.version
    }
    this.updates.push(update)
    this.doc = changes.apply(this.doc)
    this.version++
    for (let client of this.clients) this.sendUpdate(client, update)
  }

  sendUpdate(client: ActiveClient, update: StoredUpdate) {
    send(client, {
      type: "update",
      changes: update.changes.toJSON(),
      clientID: update.clientID,
      version: update.version
    })
  }
}

在真实的服务器环境中，您需要采取更加谨慎的防御措施，以确保发送畸形输入的客户端无法破坏您的服务器进程。此外，您通常还需要将更改和文档快照存储在某种数据库中，以便在服务器需要重启时能够恢复数据。但总体而言，这就是协作服务器的基本架构。

客户

客户端由两部分组成：一个用于连接服务器并设置编辑器配置的函数，以及作为该配置一部分、负责管理与服务器通信的插件。

初始化函数接收一个指向服务器的通道和一个 Wordgard 配置对象，并（异步）返回一个已连接到该服务器的编辑器实例。

async function client(channel: Channel, spec: Wordgard.Spec) {
  let first = await channel.messages.next()
  let msg = JSON.parse(first.value!) as ServerMessage
  if (msg.type == "error") {
    throw new Error(msg.error)
  } else if (msg.type == "state") {
    return Wordgard.create({
      ...spec,
      config: [
        collab({clientID: msg.clientID, startVersion: msg.version}),
        Wordgard.Plugin.define(
          editor => new ClientPlugin(editor, channel)),
        // 其余配置已在规范中给出
        (spec.config as GardState.Extension | undefined) || []
      ],
      doc: msg.doc
    })
  } else {
    throw new Error("Unexpected message: " + msg)
  }
}

由于在创建编辑器之前需要知道某些信息（例如文档和客户端 ID），因此该函数会从服务器通道读取第一条消息，查找包含我们所需数据的 "state" 消息。

collab 扩展由 "wordgard/collab" 提供，用于跟踪待处理的本地更改。ClientPlugin 是该示例的一部分，负责与服务器进行实际通信。

class ClientPlugin {
  editor: Wordgard
  channel: Channel

  constructor(editor: Wordgard, channel: Channel) {
    this.editor = editor
    this.channel = channel
    this.listen().catch(e => {
      Wordgard.logException(
        this.editor.state, e, "Client listener crashed")
    })
  }

这再次运行一个异步循环，从服务器读取消息。初始化后，我们期望接收的唯一消息是更新和错误。更新通过调用 collab.receive 进行处理。由于在接收远程更改后可能需要重新提交待处理的更改，因此如有必要，我们会安排发送操作。

  sentCurrent = false

  async listen() {
    for await (let json of this.channel.messages) {
      let msg = JSON.parse(json) as ServerMessage
      if (msg.type == "update") {
        this.editor.dispatch(collab.receive(this.editor.state, [{
          changes: ChangeSet.fromJSON(
            this.editor.state.schema, msg.changes),
          clientID: msg.clientID,
          version: msg.version
        }]))
        this.sentCurrent = false
        if (collab.hasUnsentUpdate(this.editor.state))
          this.scheduleSend()
      } else if (msg.type == "error") {
        throw new Error(msg.error)
      } else {
        throw new Error("Unexpected server message: " + json)
      }
    }
  }

update 方法会在编辑器状态发生更改时被调用。当文档发生更改时，我们会安排发送。

更新会在短暂延迟后发送至服务器，以便将部分更新合并处理。当变更已发出后，sentCurrent 标志会被设置，直到收到来自服务器的更新响应为止，以防止客户端反复尝试发送相同的变更。

  update(update: Wordgard.Update) {
    if (update.docChanged) this.scheduleSend()
  }

  scheduled = -1

  scheduleSend() {
    if (this.scheduled < 0)
      this.scheduled = setTimeout(() => this.sendUpdate(), 100)
  }

  sendUpdate() {
    this.scheduled = -1
    if (this.sentCurrent) return
    let update = collab.sendableUpdate(this.editor.state)
    if (update) {
      this.channel.send(JSON.stringify({
        type: "update",
        changes: update.changes.toJSON(),
        version: update.version
      }))
      this.sentCurrent = true
    }
  }
}

一个完善的客户端还需要以某种方式处理断开连接的情况。您需要扩展协议，允许客户端声明其已在特定文档版本上拥有编辑器，以便服务器能够发送其重新同步所需的新变更。

更正

由 receive 创建的事务会标记上 Transaction.remote 注解。像撤销历史这样的组件会自动对这些事务进行特殊处理，以便每个客户端只能撤销自己的更改，而无法撤销远程更改。

远程事务也会阻止修正对其生效。事务扩展器（修正功能所依赖的机制）在处理协作变更时更难正确实现——如果两个单独不会触发修正的变更以某种方式合并后触发了修正，那么若不加以小心，每个客户端都会单独应用该修正，从而导致混乱（甚至可能引发无限的重修正循环）。

但是，如果您不应用针对远程更改的修正，就无法再依赖其检查的强制执行，合并后的更改可能会导致您的文档中出现非矩形表格等问题。因此，如果您告知 wordgard/collab，它将特殊处理这些修正。它会在receive中，当本地待处理更改进行转换时应用这些修正，并将其调整（如有）作为本地待处理更改的一部分进行存储。这样，特定的一方（即提供导致问题的更改的客户端）负责应用修正，从而避免混淆。

当您允许服务器转换变更时，会遇到相同的问题，并采用相同的解决方案：告知服务器这些修正，以便它在转换变更时也能应用这些修正。向服务器提供与客户端完全相同的修正集至关重要，因为该协议依赖于客户端和服务端转换产生相同的输出。
