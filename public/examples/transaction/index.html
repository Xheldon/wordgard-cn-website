示例：交易分发

分发事务是指当您希望更改编辑器内容、移动选区、滚动显示某部分内容、更改扩展的状态、重新配置或以其他某种方式影响编辑器时所执行的操作。

文档变更

一种非常常见的操作是修改文档。例如，假设我们正在编写一个函数，用于在选区处插入给定的单词，您可以编写如下代码：

function insertWord(wg: Wordgard, word: string) {
  let {from, to} = wg.state.selection.replacementRange
  wg.dispatch({
    changes: {from, to, insert: [Leaf.text(word)], fit: true},
    scrollIntoView: true,
    userEvent: "insert.word",
    selection: (cx, changes) =>
      GardSelection.near(cx, changes.mapPos(to, 1), -1)
  })
}

接受数组的 事务规范 字段（例如 changes 和 effects）也为了方便而接受单个值。因此，这里我们在 changes 下提供了一个单独的变更。

选择项具有一个 replacementRange 获取器，用于指示在覆盖该选择项插入内容时应替换的范围。此功能的存在是因为某些 自定义 选择项可能希望在此处执行特殊操作——对于常规选择项，它将直接返回选择项的完整范围。

因此，我们的 change 将该范围替换为一个令牌，即一个包含我们单词的文本叶子节点。由于我们不知道像这样替换选区是否会产生有效的文档，代码还会设置 fit 标志。这将导致构建事务变更集的 ChangeSet.create 调用确保不会发出无效的变更。在已知变更有效的情况下，您可以省略此标志。

传递给事务的其他参数包括 scrollIntoView，它指示编辑器在更改后确保光标可见；以及 userEvent，它为更改提供一个粗略（尽管有些模糊）的分类。后者并非必需，但可以帮助其他代码 识别 某些类型的事务，并对它们进行特殊处理。

最后，我们需要在插入后提供一个新的选区。由于拟合变更具有某种不可预测性，我们不能简单地将光标置于 `from + word.length` 并确信那就是单词的末尾——拟合过程可能导致变更不仅仅是精确地在该位置插入该单词。因此，代码不是传递一个选区，而是传递一个函数，该函数根据变更和变更后的状态计算出一个新的选区。

许多用于操作选区的函数都期望传入一个 上下文。这使它们能够获取当前文档及其文本方向的信息。编辑器状态可视为一种上下文，但在创建事务的过程中，新状态尚不可用，因此选区创建回调会接收一个临时上下文。GardSelection.near 用于查找给定位置附近的游标位置。我们可以将变更后的位置（通过对变更集进行位置映射获得）传递给它，并使其向后扫描，以找到插入单词之后的游标位置。

这通常是文档变更事务中最棘手的部分——找到合适的新选区。变更集上的 findInserted 方法在此处也可能很有用。

可以将多个更改作为数组传递。例如，这将把整个文档包装在引用块中：

wg.dispatch({
  changes: [
    {from: 0, insert: [Blockquote]},
    {from: wg.state.doc.length, insert: [Plot.End]}
  ]
})

此类数组中提供的所有更改均相对于起始文档进行解释，而非相对于此前更改生成的文档。因此，此处的第二个更改无需为第一个更改插入的标记调整文档末尾的位置。

如果您已经创建了一个 ChangeSet 对象，也可以直接将其传入 changes 字段。

要添加或删除标记，请使用不同的变更对象表单。这些表单不使用 insert 字段，而是使用 add 来添加标记，或使用 remove 来删除标记。

// 一切皆强！
wg.dispatch({
  changes: {from: 0, to: wg.state.doc.length, add: Strong}
})

// 移除所选内容中的所有下划线
let {from, to} = wg.state.selection
wg.dispatch({
  changes: {from, to, remove: Underline}
})

交易影响

除了文档和选区变更外，事务还可以包含效果。其中一些（例如Wordgard.scrollIntoView）已在库中定义，但您也可以定义自己的效果。

此扩展用于统计编辑器状态中发生的交易次数，并提供一种重置该计数的方法。这可能并非特别实用的功能，但它展示了一种常见的模式。

import {GardState, Transaction} from "wordgard/state"

const resetCounter = Transaction.Effect.define<number>()

const transactionCounter = GardState.Field.define<number>({
  create() { return 0 },
  update(count, tr) {
    count++
    for (let e of tr.effects) {
      if (e.is(resetCounter)) count = e.value
    }
    return count
  }
})

wg.dispatch({effects: resetCounter.of(0)})

效果的实例包含一个值，其类型在定义效果类型时声明。对效果感兴趣的代码会检查附加到给定事务的效果数组，以查看其中是否包含该效果，如果包含则进行处理。is 方法 既检查效果是否为给定类型，如果是，还会告知 TypeScript 其 value 字段的类型。

某些类型的影响包含文档位置或其他依赖于文档的数据。对于这些情况，您应定义一个映射函数，以便它们能够安全地通过变更进行转换。（当事务规范被组合或事务被扩展时，就会出现这种情况。）

const highlightEffect = Transaction.Effect.define<
  {from: number, to: number}
>({
  map: (range, changes) => ({
    from: changes.mapPos(range.from, -1),
    to: changes.mapPos(range.to, 1)
  })
})

效果还提供了一种使非文档更改可撤销的方法。历史记录模块提供了一个 history.invertedEffects 方面，可用于为给定的事务提供反向效果。这些效果将存储在历史记录中，并包含在用于撤销（或重做）更改所分派的事务中。

交易对象

dispatch 方法接受事务 规范 或 Transaction 对象。通常，将规范作为对象字面量传递更为方便，但如果您需要初始化一个实际的事务对象，可以使用 state.update。

let tr = state.update({selection: {anchor: 1}})
console.log(tr.state.selection.head)

此类事务对象提供了与其规范中大部分相同的字段，但经过规范化处理（例如 changes 始终包含一个变更集，selection 包含 null 或完整的选区，等等）。状态字段 更新函数 和 更新监听器 所看到的正是这些对象。

完全可以在编辑器组件之外处理事务。这在测试中尤其有用，但也可用于在浏览器之外运行脚本化或保存的编辑会话。

某些辅助函数或函数式命令会返回事务规范。将多个此类规范合并为单个事务可能很有用。您可以使用Transaction.merge来实现这一点。这些规范将被合并，生成一个新的规范，其中包含它们变更、注释和效果的并集。

默认情况下，两个规范中的更改均指向初始文档。如果您因某种原因拥有指向由先前事务规范生成的文档的更改和效果，您可以设置 sequential 标志，以确保它们被正确解释。

// 将 B 直接插入到 A 之后
let tr = state.update(Transaction.merge(state, {
  changes: {from: 3, insert: [Leaf.text("A")]}
}, {
  changes: {from: 4, insert: [Leaf.text("B")]},
  sequential: true
}))

扩展器

Wordgard 允许您 注册 函数，这些函数可以为每笔交易添加额外的元素（变更、效果、注释等）。

这使得诸如修正以及其他保持不变量的扩展成为可能。它还有一些侵入性较小的用途，例如确保事务获得其他代码所依赖的特定注释或效果。

此示例定义了一个扩展器，通过在选择落入该范围时将其移至该范围之外，确保选择永远不会位于位置 5 和 10 之间。

import {Transaction, GardSelection} from "wordgard/state"

const jumpyCursor = Transaction.extender.of(tr => {
  if (tr.newSelection.from >= 10 || tr.newSelection.to <= 5)
    return null
  let moved = tr.startState.selection.from <= 5 &&
              tr.newDoc.length > 10
    ? GardSelection.near(tr.state, 10, 1)
    : GardSelection.near(tr.state, 5, -1)
  return {selection: moved}
})

这显然是一个强大的工具，若使用不当可能会引发问题。您需要仔细考虑在哪些情况下希望您的扩展器（或修正器）被触发，以及它如何可能阻止用户执行他们本应合理能够完成的操作。

扩展器的存在是负责分发事务的代码必须牢记的一点。您不能假设在事务执行后，编辑器状态恰好是您事务规范所产生的结果。此外，您在事务中包含的效果或注解中嵌入此类期望时，必须格外谨慎。

一个类似但更温和的功能是 事务追加器。它们可以导致编辑器在响应其他事务时立即分派额外的事务。例如，输入规则 就使用了这种机制，它们希望其效果紧随原始输入之后，但又能被单独撤销。
